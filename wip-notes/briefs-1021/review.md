## 怎么做
1. 先读 `common.md`（同目录）和那块活的任务书；读它的汇报。
2. 用它的工作树（`/home/user/inkwave/.claude/worktrees/<分支>`、`/home/user/IELTS-Base/.claude/worktrees/<分支>`；不在就 `git worktree add <目录> <分支>`），`git fetch origin <分支>` 确认和远端一样、工作区干净。看完整的 diff（`git diff io/hopeful-turing-fnxytg...<分支>`，两个仓库都看）。
3. 找这几类（每一条都要有能复现的证据：一条命令、一个测试、一段日志、一张截图，不收「可能」）：
   - **做没做到**：任务书的每一条「要做的」逐条对：做了、做对了、有测试守着？业主原话要的东西（卡死、很卡、先选玩法、不走 CI 交付）落到她手上是什么样？
   - **正确性**：边界、横竖屏、减少动态效果、手柄 / 键盘、没有数据 / 有她的数据、第 1–3 周和第 4 周以后、复习日、Boss、双人；竞态（异步、动画、存储事件）；异常路径（起不来、超时）。
   - **她的数据**：写她账号的每一处照 §39 / §41（写前重读、只改要改的、不建、幂等、她的时区），有没有用真的经典页做的「同一份记录」对照测试；隐私（`my-progress.*`、截图、夹具）。
   - **测试有没有被放宽**：改了的断言是改成测新的行为，还是变松了 / 删了 / 加了超时 / 跳过了。
   - **数字**：汇报里的性能 / 体积 / 计数，挑最关键的一两个自己重量一次（同一台机器、锁里）。
   - **界面**：§47 的规矩（一样东西一种材质、中文不描边、字不出框、对比度、≥ 44 pt、safe area），截图看过。
   - **合并风险**：和其他三条分支（`wf-softlock`、`wf-classic`、`wf-perf`、`wf-artifact-game`）会撞的地方，生成的文件。
4. **修**：确认的问题直接在同一个分支上修（小步提交、推送，末尾两行照 common.md），补上能抓住它的测试。改动大到超出「修」的（重新设计），别做，写进汇报。
5. 修完把相关的测试全跑一遍（锁里），确认没有新的红。
